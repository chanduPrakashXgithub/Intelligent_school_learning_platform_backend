# F0.5 — API Routing and Versioning

## 1. Task ID and Task Name
- **Task ID**: `F0.5`
- **Task Name**: API Routing and Versioning

## 2. Objective
Establish a clean, modular, and version-controlled API routing infrastructure mounted under `/api/v1` to allow smooth evolutionary updates without breaking client applications.

## 3. Why This Task Is Necessary
Modular Monolith architectures require decoupled route registration so that individual domain modules (e.g. `auth`, `classes`, `timetable`, `studio`) can register their endpoints independently without cluttering the main Express application file. Versioning ensures future backward-incompatible API changes can be introduced under `/api/v2` without disrupting existing clients.

## 4. Architecture and Implementation Approach
- **Master Version Router**: `src/routes/v1/index.js` acts as the single aggregator for all version 1 domain sub-routers.
- **Root Mounting**: Mounted in [src/app.js](file:///E:/School_Learning_platform/backend/src/app.js) via `app.use(API_PREFIX, v1Router)`, where `API_PREFIX = "/api/v1"`.
- **Sub-Router Decoupling**: Each module exports its own Express Router mounted to its designated resource path prefix:
  - `/api/v1/health` $\rightarrow$ `healthRoutes`
  - `/api/v1/auth` $\rightarrow$ `authRoutes`
  - `/api/v1/classes` $\rightarrow$ `classesRoutes`

## 6. Explanation of Important Functions and Components
- `v1Router`: An Express Router combining sub-routers:
  ```javascript
  router.use("/health", healthRoutes);
  router.use("/auth", authRoutes);
  router.use("/classes", classesRoutes);
  ```
- Unmatched Route Interceptor: Defined in `src/app.js` after route registration, catching all unhandled requests and passing a `NotFoundError` to the centralized error handler.

## 7. Execution Flow
```
HTTP Request ➔ /api/v1/... ➔ v1Router ➔ Matching Module Router ➔ Middleware Pipeline ➔ Controller Handler
HTTP Request ➔ /unmatched ➔ NotFoundError ➔ Central Error Handler ➔ 404 Response
```
