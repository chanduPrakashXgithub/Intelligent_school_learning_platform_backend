# F0.8 — Authentication Integration

## 1. Task ID and Task Name
- **Task ID**: `F0.8`
- **Task Name**: Authentication Integration

## 2. Objective
Implement stateless JSON Web Token (JWT) issuance and verification, password hashing using bcrypt, and live database account/school verification, ensuring secure caller identification on all protected endpoints.

## 3. Why This Task Is Necessary
The platform must verify the caller's identity before granting access to educational assets, student records, or teaching workflows. Stateless JWTs avoid server-side session bottlenecks, while live database checks ensure deactivated teachers or suspended schools cannot continue accessing the platform with previously issued tokens.

## 4. Architecture and Implementation Approach
- **Pluggable Non-Duplicative Design**: The authentication layer uses the shared `users` table without introducing duplicate identity stores.
- **Token Signing**: Uses HMAC-SHA256 (`HS256`) with `issuer: "school-learning-platform"` and `audience: "school-learning-platform-api"`.
- **Claims**: Includes `userId`, `schoolId`, `role`, and `teacherId`.
- **Live Database Status Verification**: The `authenticate` middleware decodes the token, checks signature validity and expiration, and performs an indexed database query against `users` and `schools` to ensure:
  1. `users.is_active = 1`
  2. `schools.is_active = 1`
  3. `users.role` matches the token role (preventing privilege desynchronization).
- **Frozen Identity**: Attaches an immutable `req.user` object to the request.

## 6. Explanation of Important Functions and Components
- `authenticate(req, res, next)`: Express middleware extracting the `Bearer <token>` from the `Authorization` header, verifying it, and attaching `req.user`.
- `loginUser({ schoolCode, email, password })`:
  - Locates user by school code and email via `findUserForLogin()`.
  - Verifies account and school active status.
  - Compares password against `password_hash` using `bcrypt.compare()`.
  - Issues signed JWT token and updates `last_login_at`.
  - Returns safe user details (excluding password hash).
- `updateLastLogin(userId, schoolId)`: Records login timestamp in MySQL.

## 7. Execution Flow
```
Client POST /api/v1/auth/login ➔ validate(loginSchema) ➔ loginUser()
   │
   ├─► findUserForLogin(schoolCode, email)
   ├─► bcrypt.compare(password, password_hash)
   ├─► jwt.sign({ userId, schoolId, role, teacherId })
   ├─► updateLastLogin()
   ▼
Return { accessToken, tokenType: "Bearer", expiresIn, user: { ... } }

Protected Endpoint Request ➔ authenticate middleware
   │
   ├─► Extract Authorization: Bearer <token>
   ├─► jwt.verify(token, JWT_SECRET)
   ├─► Query MySQL: SELECT user & school active status
   ├─► Verify role matches token role
   ▼
req.user = Object.freeze({ userId, schoolId, role, teacherId }) ➔ next()
```

## 8. Database Interaction
Queries `users` and `schools` tables using parameterized queries with index utilization (`idx_users_school_role`, `idx_users_school_active`).

## 9. API Endpoints
- `POST /api/v1/auth/login`: Authenticates user credentials and returns JWT.
- `GET /api/v1/auth/me`: Verifies active JWT and returns identity and tenant context.

## 11. Security Considerations
- Password hashes use bcrypt with a cost factor of 12 salt rounds.
- Generic error messages (`"Invalid school code, email, or password"`) prevent user enumeration attacks.
- Passwords are never returned in responses or recorded in logs.
- Immediate token revocation: Deactivating a user or school immediately prevents subsequent requests from succeeding.
