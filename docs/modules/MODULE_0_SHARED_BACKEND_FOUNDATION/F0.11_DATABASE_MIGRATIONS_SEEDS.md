# F0.11 — Database Migration and Seed Strategy

## 1. Task ID and Task Name
- **Task ID**: `F0.11`
- **Task Name**: Database Migration and Seed Strategy

## 2. Objective
Establish an idempotent, distributed-locked, version-controlled database schema migration engine and deterministic pilot school seed scripts for MySQL 8.4 Server.

## 3. Why This Task Is Necessary
Manual schema modifications result in environment drift, broken foreign keys, and untracked changes across development, staging, and production. An automated, checksummed migration runner guarantees reproducible database setups, while seed scripts populate baseline pilot data (schools, classes, subjects, teacher accounts) for testing.

## 4. Architecture and Implementation Approach
- **Distributed Concurrency Lock**: `src/database/migrator.js` executes `SELECT GET_LOCK('school_learning_platform_migrations', 10)` before running migrations. This ensures multiple app instances booting simultaneously do not execute migrations concurrently.
- **Tracking Table**: Creates `schema_migrations` to record `version`, `filename`, `checksum`, and `applied_at`.
- **Integrity Checksumming**: Computes the SHA-256 hash of each migration file. If an already-applied migration file is altered on disk, the runner halts with an error.
- **Idempotent Seed Scripts**: Seed scripts use `ON DUPLICATE KEY UPDATE` to allow safe repeated executions without duplicating records.
- **Relational Seed Ordering**: Sections are created before teacher assignments so that `@section_id` foreign keys resolve properly on fresh databases.

## 6. Explanation of Important Functions and Components
- `runMigrations()`:
  - Acquires MySQL distributed lock.
  - Ensures `schema_migrations` table exists.
  - Reads SQL files in lexicographical order (`001_*.sql`).
  - Verifies SHA-256 checksums of applied migrations.
  - Executes unapplied statements and records them atomically.
  - Releases distributed lock in `finally`.
- `001_core_foundation.sql`:
  - DDL for `schools`, `academic_years`, `classes`, `sections`, `subjects`, `users`, `teacher_assignments`.
  - Composite unique indexes and foreign keys enforcing school isolation.
- `001_pilot_school_seed.sql`:
  - Pilot school (`PILOT-001`, `Pilot School`).
  - Academic year `2026-2027`.
  - Classes 1–10.
  - 5 Subjects (`MATH`, `SCI`, `ENG`, `SOC`, `CS`).
  - Sections A and B for all classes (20 sections total).
  - Deterministic administrator (`admin@pilotschool.example`) and teacher (`teacher@pilotschool.example`).
  - Teacher assignment to Section 1 (Class 1-A).

## 7. Execution Flow
```
npm run migrate ➔ scripts/migrate.js ➔ runMigrations()
   │
   ├─► SELECT GET_LOCK(...)
   ├─► CREATE TABLE IF NOT EXISTS schema_migrations
   ├─► Read migrations/ directory
   ├─► For each .sql: Compute SHA-256 ➔ Check schema_migrations
   │   ├─► Already applied: verify checksum, SKIP
   │   └─► Not applied: execute statements, INSERT INTO schema_migrations
   ▼
RELEASE_LOCK(...) ➔ closeDatabasePool() ➔ Exit 0
```

- SHA-256 checksum verification prevents historical migration tampering.
